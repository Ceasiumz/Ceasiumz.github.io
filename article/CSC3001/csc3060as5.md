
## Static Latency Model

### (a) load 5 cycles, store 1 cycle

Since load must fetch a value that later instructions may consume, while store does not produce a register result and is simplified as a short operation.

### (b) static model reasonable

A compiler cannot know runtime behavior exactly, but a fixed approximate model is still useful for guiding scheduling decisions.

---

## Dependency Detection

### (a) why not RAR

**
Reads do not modify state, so two reads do not constrain each other.

### (b) why must DAG

A cycle means no valid topological order exists, so the region cannot be scheduled consistently.

---

## Priority Calculation

### (a) why WAR/WAW ordered only

WAR/WAW do not represent result availability. They only preserve read/write ordering, and under this simplified model issuing the predecessor is enough to establish that order.

---

## Tie-Breaking

### (a) why MOST_CHILD better

It may unblock more successor instructions earlier, increasing future scheduling flexibility.

### (b) when LPT better than SMALLER_INDEX

When a long-latency and a short-latency instruction are both ready with equal priority, issuing the long one first often gives more opportunity to hide its latency.

---

## Complexity Analysis
### Definitions

| Symbol | Meaning                              |
| ------ | ------------------------------------ |
| **N**  | Total instructions / DAG nodes       |
| **E**  | Total edges in the DAG               |
| **R**  | Ready-list size at any cycle (R ≤ N) |
| **F**  | Inflight size at any cycle (F ≤ N)   |
| **L**  | Maximum instruction latency          |
| **C**  | Total cycles elapsed (C ≤ N + L)     |


### (a) naive scheduling
computePriorities   once per node and edge O(N + E)            
Rebuild ready list   C cycle, each cycle finding ready nodes needs O(N),   O(N) × C = O(N²)  
Select best node    C cycle, 1 issue per cycle, O(R) per issue, O(R) × C = O(N²)
Remove issued node   N nodes, 1 shift for every node, O(R) per shift, O(R) × N = O(N²)
Insert newly-ready      O(1) per push_back, N pushed, O(1) × N = O(N)
Inflight retire scan    C cycle, each cycle detect retired nodes needs O(F), O(F) × C = O(NL) 
Edge relaxation         O(E)        
Final answer: O(N^2 + NL + E) or O(CN + E) and we could suppose C = O(N + L).

### (b) recursive memorized priority

Each node and edge is visited exactly once, so it is O(N + E).

### scheduleFast() — Optimized: O((N + E) log N)
schedule_fast()
scheduleFast() replaces both two heaps that are only ever touched when a node actually changes state:

Max-heap (ready) — keyed on (priority, tie-break). A node is pushed exactly once when its last predecessor is satisfied and popped exactly once when issued. Cost: O(log N) per push/pop.

Min-heap (inflight) — keyed on finish_cycle. A node is pushed at issue time and popped when finish_cycle == current_cycle. Cost: O(log N) per push/pop.
#### breakdown

 1. computePriorities — O(N + E) (unchanged)

 2. Set readyHeap — O(N log N)

 3. While loop — driven purely by _events_, not clock ticks

| Event                             | Occurrences | Cost each | Total      |
| --------------------------------- | ----------- | --------- | ---------- |
| readyHeap.pop() (issue)           | exactly N   | O(log N)  | O(N log N) |
| inflightHeap.push() (issue)       | exactly N   | O(log N)  | O(N log N) |
| inflightHeap.pop() (retire)       | exactly N   | O(log N)  | O(N log N) |
| tryRelease → readyHeap.push()     | at most E   | O(log N)  | O(E log N) |
| Idle cycles (no issue, no retire) | at most L   | O(1)      | O(L)       |
|                                   |             |           |            |
|                                   |             |           |            |

#### Overall scheduleFast()

O((N+E) log N)​
Specifically, for sparse DAGs where E = O(N): O(N log N).

####  Comparison with naive scheduler

```
                        schedule()          scheduleFast()
────────────────────────────────────────────────────────────────────
computePriorities       O(N + E)            O(N + E)
